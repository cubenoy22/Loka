# ScrapbookUI bake/ByteSource shape review

Ranked candidates considered for the bake and file-source slice:

1. **Classic and modern manifests deliberately repeat the same logical
   directory.** This is the strongest bolted-on shape: two files must agree on
   bags, IDs, kinds, and names while their source extensions differ. The bake
   runs both manifests through `lrpc` and compares their derived stamps before
   installing either package. A mutation from asset 1004 to 1014 was refused
   with distinct stamps, and both previously installed packages retained their
   hashes. The duplication is kept at the environment gate rather than moved
   into runtime encoding policy.
2. **`ScrapbookByteSource` names one of two parallel transport doors.** A
   runtime base pointer plus allocation would add ownership and nullability only
   to select a build-time fact. The conditional typedef leaves one concrete,
   directly owned source member: Toolbox opens the resolved `FSSpec`; Win32 and
   macOS open the resolved native display path through `StdioByteSource` and
   its platform `OpenRead` seam. `Reader` still borrows the same `ByteSource`
   interface, and `close()` remains the single teardown path.
3. **The generator now emits two representations from one placeholder-art
   description.** PICT and PNG encoding loops are separate because their file
   mechanisms differ, but page roster, pattern facts, dimensions, and badge
   intent have one home in `generate_picts.py`. No third-party art, runtime
   decoder, or encoding field enters application code.
4. **The committed modern package and PNG files are generated artifacts.**
   They are required because platform builds must not download or convert at
   runtime. `regen-assets.sh` owns their construction, stages both package
   families in a task-specific temporary directory, checks the id-space wall,
   and then lets `lrpc` commit each final package/stamp pair
   failure-atomically. The classic package's byte hash remains
   `e54677ba72bc788d33cf644cbccb23dd048a1b36a1e27954b27cafebdf5914df`.
5. **The package pin finds repository fixtures from `__FILE__`.** This is a
   test-only path seam, not a shipped API chosen for observability. It avoids a
   production accessor and reads both manifest and package through platform
   file seams. The test checks every manifest row's bag/id/kind and the PNG
   signature of every image payload, then maps logical `ASSETS.LRP` to the
   fixture through a host context and loads the package's text page.

Implementation-complete gate:

- Added doors/fields: the `ScrapbookByteSource` build-time alias replaces the
  Toolbox-only member type; it parallels the two existing `ByteSource`
  implementations without adding a new lifetime regime.
- Added call sites: one modern `source_.open(displayPath)` branch parallels the
  Classic `source_.open(spec)` branch. Both converge immediately on the same
  `Reader::beginOpen` and existing close/failure paths. Mutating the modern
  branch to refuse all opens makes the new package test fail at
  `package.open(&context)`.
- Added teardown: only the host bake script's exact `mktemp` directory has a
  new trap cleanup. Runtime teardown is unchanged and still closes Reader
  before source.
- Configuration absence: id-space equality is enforced by the regeneration
  script in every bake; it is not a debug-only or compiler-gated diagnostic.
- Test-observability APIs: none were added to shipping code.
