# ScrapbookUI portable-presentation shape review

Ranked candidates considered for the portable UI slice:

1. **Two button action doors parallel the former scrollbar door.** `previousPage_`
   and `nextPage_` are both emitter fields, so they initially read like a
   duplicated family. They remain separate because the shared `Button` contract
   emits an action without a direction payload, and the two names expose the
   distinct user intents. Each field is read by composition and owned/bound by
   `MainNode`; there is no dotted ownership line or platform branch.
2. **The selected page could have remained a live `NodeState<int>` after the
   scrollbar disappeared.** That would leave an observed-state-shaped field
   with no observing child. The slice instead keeps `selectedPage_` as narrow
   owner-local mutable state: the navigation actions change it, and the page
   Flow reads it. No new state owner, binding, or cleanup path is introduced.
3. **The page-kind badge could have gained an environment/encoding field.**
   Such a field would exist only so the UI could display bake provenance it
   does not own. The presentation keeps its existing badge fact and changes the
   image value to neutral `IMAGE`; PNG versus PICT remains outside the runtime
   UI contract.
4. **Endpoint behavior could have been split across the two callbacks.** That
   would duplicate the range wall and let one direction drift. Both actions go
   through the existing always-on `selectPage()` clamp and same-value return,
   so absence of a platform control or debug-only check cannot turn an
   out-of-range request into invalid package access or redundant page work.
5. **Public navigation accessors could have been added for tests.** No API was
   added for observability. The existing `selectPage()`/`selectedPage()` seam
   remains the only programmatic page-selection surface.
6. **The host pin needs MainNode before the later ByteSource slice makes its
   package portable.** `ScrapbookNavigationTests.cpp` therefore compiles the
   real node source in a private test namespace against a deterministic package
   probe. This is deliberately test-only mechanism: it adds no shipping seam,
   avoids pulling PR-B ownership into PR-A, and the namespace rename prevents
   an ODR collision once the real package test joins the next stack level. The
   probe has one reset static because the test process owns one bounded
   scenario; no application state or cleanup path depends on it.

No reclamation or teardown path changes in this slice. Both new emitter
bindings are owned by the existing `ComposableNode` callback ledger and retire
through its existing detach/destruction procedure.

Implementation-complete gate:

- New test source/header/registry door: parallels the other contract-test
  families and adds one registered test, not a second runner or lifecycle.
- New test probe fields: `prepareCount_` and `currentPage_` are read and reset
  only inside the bounded fake package; they parallel the page-load and
  published-page observations in the Toolbox scenarios.
- New production wall: the post-clamp equality return is always on in every
  build. Without it the consequence is redundant decode/publish work, not an
  undetected ownership or memory-safety failure.
- Teardown/reclamation: unchanged; the null-platform test declares the
  platform before the Scene so Scene detach completes before platform teardown.
- Mutation evidence: the pin fails when the Previous binding is removed, when
  the two directions are swapped, and when the endpoint early return is absent.
