# ScrapbookUI Win32-arm shape review

Ranked candidates considered for the Win32 slice:

1. **The new target parallels every existing Win32 example target.** A
   platform bootstrap is necessarily a repeated seam, but this one adds no
   application behavior or platform handle ownership: `WinMain` hands the
   existing `ScrapbookAppConfig` to `RunApp`, and `ScrapbookUIWin32` links the
   existing `LokaWin32Core` projection.
2. **Package staging renames an environment-specific source artifact.** The
   CMake `configure_file` call is an extra packaging step beside executable
   creation. It is kept adjacent to the Win32 target and stages
   `assets/ASSETS-modern.LRP` as `ASSETS.LRP`, preserving the single
   `File::Application()` runtime contract instead of adding a platform package
   name to application code.
3. **`main.cpp` now has a second compile-time entry door.** A separate Win32
   file would duplicate the same two-line `RunApp` bootstrap and add another
   source list decision. The closed preprocessor family keeps platform entry
   signatures visible and has an explicit unsupported-platform error.
4. **The shared `USE_CONSOLE_SUBSYSTEM` option repeats existing example
   vocabulary.** It intentionally reuses the repository's established Win32
   debugging switch rather than minting a Scrapbook-only flag. Both target
   forms share identical sources, warnings, includes, link ownership, and
   package staging.
5. **Win32 text/path loss could hide behind existing APIs.** The added lines
   contain no `...A` entry point and no unsuffixed text/path Win32 call.
   `ScrapbookPackage` opens the application-relative path through
   `Win32PlatformContext` and `StdioByteSource`/`OpenRead`; image bytes continue
   through the existing WIC `createImageFromBlob` implementation.

Implementation-complete gate:

- New door/call site: the `WinMain` branch parallels the existing Retro68
  `main` branch and converges immediately on `RunApp<ScrapbookAppConfig>`.
- New target: `ScrapbookUIWin32` parallels the HelloWorld, MineSweeper, and
  SimpleViewer targets; it adds no state, virtual, callback, or platform field.
- Teardown/reclamation: unchanged. The app/core and package owners retain their
  existing close paths.
- Configuration-gated checks: none protect memory or path correctness. The
  only configuration choice is console versus GUI subsystem.
- Verification status: the required `/mnt/c` worktree, MSVC builds, runtime
  capture, and mutation evidence must be recorded from the supplied real-machine
  procedure; they cannot be substituted by a WSL build.
